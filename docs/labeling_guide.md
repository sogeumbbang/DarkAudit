# DarkAudit 라벨링 규칙서

> 현재 구현 대조 · 2026-10-08
> 관련 파일: `rules/dark_pattern_rules.yaml` (v0.3.0), `rules/label_schema.json` (1.0)

이 문서는 합성 데이터의 라벨 작성 기준이다. 15개 유형의 라벨 형식을 정의하지만 현재 자동 탐지·기본 평가는 DA-03·04·07·12·15만 대상으로 한다. 배포 입력 상한은 6장이고 기존 평가 데이터는 Flow당 5화면이다. 두 수치를 혼동하지 않는다.

현재 평가셋은 보험 9쌍·예적금 2쌍, 총 22 Flow·110화면의 생성기 기반 라벨이다. 독립 검수자가 확정한 Gold Set과 라벨러 일치도 측정은 완료된 결과가 없다. 아래 검수 절차는 후속 작업 기준이며 실측 결과가 아니다. 실제 지표의 분모·매칭 구현은 [평가 실행 가이드](evaluation-framework.md), 측정 결과는 [평가 요약](evaluation.md)를 따른다.

관계 요소의 필수 조건은 라벨·분석 계약의 요건이다. 현재 요소 평가는 규칙·화면·대표 bbox의 IoU를 기준으로 일대일 매칭하므로, 아래 관계 작성 기준을 곧바로 관련 요소 별도 채점이 구현됐다는 뜻으로 읽지 않는다.

---

## 왜 이 문서가 필요한가

Rule Base 는 **무엇을 탐지할지**를 정했다. 이 문서는 **무엇을 정답으로 칠지**를 정한다.

기준이 없으면 Team B 는 "Screen 2의 체크박스가 DA-04"라고 라벨하는데 Team A 의 모델은 "Screen 2에 DA-04가 있음"이라고 출력할 수 있다. 둘 다 틀린 말이 아니지만 비교가 불가능하다. 그 상태로 Precision·Recall 을 재면 **모델 성능이 아니라 두 사람의 기준 차이를 재게 된다.**

합의의 목적은 같은 것을 같은 방식으로 부르는 것이다.

## 결정 ① 라벨의 단위

### 구조 — primary + related

모든 element 라벨은 **대표 요소 하나(primary)** 를 갖고, 관계를 구성하는 상대가 있으면 `related_elements` 에 덧붙인다.

```
DA-03  primary = 강조된 선택지    related = [억제된 선택지]
DA-04  primary = 사전선택된 체크박스   related = []
```

단위를 유형마다 다르게 두는 대신 형식을 하나로 통일했다. 라벨러가 "이건 element 인가 pair 인가"를 매번 판단하지 않아도 되고, 평가 로직도 갈라지지 않는다.

### 관계가 필수인 유형

`related_elements` 가 비면 오답으로 처리하는 유형이 세 개 있다. 관계 자체가 위반 요건이라 상대 요소가 없으면 판정이 성립하지 않기 때문이다.

| ID | 유형 | primary → related |
| --- | --- | --- |
| DA-02 | 속임수 질문 | 질문 문구 → 대응 버튼들 |
| DA-03 | 잘못된 계층구조 | 강조된 선택지 → 억제된 선택지 |
| DA-11 | 반복간섭 | 최초 요구 요소 → 반복 출현들 |

이 세 유형에서 primary만 쓰고 related를 비우면 관계 근거가 불완전한 라벨이다. DA-03 의 본질은 버튼 하나가 아니라 두 버튼의 차이이므로, 관계 근거를 반드시 기록해야 한다. 현재 평가기의 대표 bbox 점수와 관계 근거 검수는 구분한다.

나머지 유형은 `related_elements` 가 선택이다. 있으면 근거가 풍부해지고 없어도 감점하지 않는다.

### 특이 케이스 두 가지

**DA-01 은 부재를 라벨한다.** 다른 유형은 화면에 있는 것을 가리키지만 이것은 "확인 페이지가 없다"를 기록한다. 가리킬 bbox 가 존재하지 않아 라벨 형식이 근본적으로 다르다. MVP 우선순위 P2 에 둔 이유이기도 하다.

**DA-06 은 Flow 두 세트가 필요하다.** 가입 Flow 만으로는 판정이 불가능하고 해지 Flow 와 대조해야 한다. `label_unit` enum 에 `flow_pair` 자리는 만들어 두었으나 MVP 라벨링 대상에서는 제외한다.

## 결정 ② 완화 요건을 충족한 경우

`mitigating_checks` 를 충족한 화면은 **positive 로 라벨하되 severity 를 한 단계 낮추고 `mitigated: true` 태그를 붙인다.**

```json
{ "rule_id": "DA-04", "severity": "REVIEW", "mitigated": true }
```

예: 사전선택이 있으나 전체선택·전체취소 버튼이 함께 제공되는 화면 → DA-04 positive, severity REVIEW, `mitigated: true`

### negative 가 아닌 이유

완화 요건을 충족해도 **사전선택이 존재한다는 사실 자체는 변하지 않는다.** 달라지는 것은 그 사실의 위험도다.

이를 negative 로 두면 결정 ③ 에서 분리한 "유형 존재"와 "severity" 가 다시 뒤섞인다. 유형 판정 지표에서 이 케이스가 사라져 모델이 사전선택을 인식했는지 여부를 측정할 수 없게 된다.

Rule Base 의 `severity_policy` 역시 완화 요건 충족 시 유형 소멸이 아니라 **severity 1단계 하향**으로 정의되어 있으므로, 라벨도 이에 맞춘다.

실무적으로도 담당자에게 "사전선택이 있으나 전체취소 컨트롤이 있어 위험도는 낮음"이라고 전달하는 편이, "문제 없음"이라고 알리는 것보다 정확하다.

### 초기 상태 자체가 다른 경우와 구분

체크박스가 애초에 미선택인 화면은 사전선택이 존재하지 않으므로 유형 자체가 성립하지 않는다. 이 경우는 라벨 없음(negative)이 맞다.

| 화면 상태 | 라벨 |
| --- | --- |
| 사전선택 있음 · 전체취소 없음 | DA-04 positive, HIGH |
| 사전선택 있음 · 전체취소 있음 | DA-04 positive, REVIEW, `mitigated: true` |
| 사전선택 없음 | 라벨 없음 |

세 번째 행이 현재 Clean Flow 의 상태다. 두 번째 행에 해당하는 Flow 는 아직 없으므로, 완화 요건 처리를 검증하려면 별도 config 추가가 필요하다.

## 결정 ③ severity 를 라벨에 넣을지

**유형 존재와 severity 를 별도 필드로 분리한다.**

DA-12 가 단독으로 있는 화면은 유형은 존재하지만 HIGH 는 아니다. 두 정보를 합치면 "유형은 맞췄는데 결합 판정을 틀림"과 "유형 자체를 못 찾음"이 뭉개져 어디가 문제인지 알 수 없다.

severity 가 결합으로 승격된 경우 `combination_with` 에 근거 rule_id 를 남긴다.

```json
{
  "rule_id": "DA-12",
  "severity": "HIGH",
  "combination_with": ["DA-04"]
}
```

## 결정 ④ 위치 정확도 기준

모델이 유형은 맞췄으나 인접 요소를 가리킨 경우를 정답으로 볼지 판단하려면 bbox IoU 임계값이 필요하다. 이 값 없이는 Localization Accuracy 를 계산할 수 없다.

일반적인 객체 탐지에서는 0.5 를 쓰지만 금융 UI 는 요소가 작고 밀집해 있어 더 높여야 할 수 있다. 특히 체크박스는 화면에서 차지하는 면적이 작아 조금만 어긋나도 IoU 가 급격히 떨어진다.

**평가기 기본 IoU 임계값은 0.5다.** 작은 요소는 라벨 작성·사람 검수 시 전체 클릭 영역이나 중심점도 확인한다. 중심점 포함은 현재 자동 채점의 대체 적중 기준으로 구현되어 있지 않다.

정답 라벨끼리는 bbox 를 사람이 그리지 않으므로 불일치가 발생하지 않는다. 이 임계값은 **모델 출력과 정답 라벨을 비교할 때만** 적용된다.

---

## 결정 ⑤ 한 요소에 여러 유형이 걸릴 때

**Multi-label 을 허용한다.**

사전선택된 체크박스가 시각적으로도 강조되어 있으면 DA-04 와 DA-03 이 동시에 해당한다. Rule Base 에 `combination_amplifiers` 를 정의해 두었는데 single-label 로 라벨하면 결합 자체를 데이터로 표현할 수 없다.

모델 출력도 multi-label 이어야 하며, 평가는 유형별로 독립 계산한다.

---

## 결정 ⑥ 판단이 갈릴 때

1. **1차 기준은 가이드라인 원문 조항.** 해당 유형의 정의와 준수사항을 함께 읽고 판단한다.
2. **원문으로도 갈리면 데이터셋에서 제외하고 `deferred` 에 기록한다.** 억지로 라벨한 애매한 데이터가 평가 지표를 가장 심하게 오염시킨다.
3. 보류 항목이 쌓이면 주기적으로 다시 검토한다. 유사 케이스가 여러 개 모이면 규칙서에 판정 예시로 추가한다.

미리 정하지 않으면 그때그때 목소리 큰 쪽으로 결정된다.

## 라벨 파일 형식

정식 정의는 `rules/label_schema.json`을 따른다. 아래는 형식 설명용 한 화면 예시이며 실제 평가 라벨의 발췌가 아니다.

```json
{
  "schema_version": "1.0",
  "flow_id": "ins-001-risky",
  "variant": "risky",
  "pair_id": "ins-001",
  "sector": "insurance",
  "flow_type": "join",
  "screens": [
    { "screen_index": 1, "image": "ins-001-risky/01.png",
      "viewport": { "width": 390, "height": 844 } }
  ],
  "labels": [
    {
      "rule_id": "DA-04",
      "label_unit": "element",
      "primary": {
        "screen_index": 1,
        "bbox": [0.08, 0.42, 0.06, 0.03],
        "text": "안심케어 서비스 +3,000원",
        "element_type": "checkbox"
      },
      "related_elements": [],
      "severity": "HIGH",
      "mitigated": false
    }
  ],
  "deferred": []
}
```

bbox 는 화면 크기로 나눈 0~1 정규화 좌표다. Figma 시안(1x), 레티나 캡처(2x), 기기별 폭 차이가 있어 절대 픽셀을 쓰면 같은 UI 도 해상도에 따라 임계값이 다르게 걸린다. 원본 크기는 `viewport` 에 따로 보관한다.

## 결정 ⑦ 같은 유형이 한 Flow 에 여러 번 나올 때

한 Flow 안에서 동일 rule_id 가 여러 화면에 걸쳐 성립하는 경우가 있다. 예: `dep-001-risky` 의 DA-07 은 S1(위험고지 축소) · S2(우대조건 접힘) · S5(중도해지 안내 축소) 세 곳에서 성립한다.

이때 이를 3건으로 셀지 1건으로 셀지에 따라 Recall 의 분모가 달라진다.

### 인스턴스 단위로 센다

DarkAudit 의 결과물은 Evidence Report 이며 담당자에게 **어느 화면 어느 요소를 수정해야 하는지** 제시해야 한다. "이 Flow 에 숨겨진 정보 문제가 있습니다"까지만 알리는 것은 실무적으로 불충분하다. 위반 지점을 빠짐없이 찾는 능력을 측정해야 하므로 각각을 별도 인스턴스로 집계한다.

### 다만 두 층으로 집계한다

| 층 | 단위 | 역할 |
| --- | --- | --- |
| **Instance-level** | 위반 지점 각각 | 주 지표. Precision · Recall · Macro F1 |
| **Flow-level** | Flow 당 유형 존재 여부 | 보조 지표 |

두 값을 함께 보면 진단이 가능하다. Flow-level 은 높은데 Instance-level 이 낮으면 유형은 인지하지만 모든 발생 지점을 찾지 못하는 상태이며, 임계값 조정으로 개선될 여지가 있다. 둘 다 낮으면 규칙 자체를 탐지하지 못하는 것이므로 접근이 달라진다. 한 지표만으로는 이 구분이 되지 않는다.

### 인스턴스 수 편중에 대한 대응

현재 추적된 라벨에서 DA-07은 7건, DA-05는 3건이다. DA-05는 현재 자동 탐지·기본 평가 범위 밖이다. 이 차이는 규칙의 난이도가 아니라 **화면을 그렇게 제작했기 때문에** 발생한 것이다. 인스턴스가 1건인 유형은 Recall 이 0 또는 1 밖에 나오지 않아 지표로서 의미가 없다.

- **유형별 최소 3 인스턴스**를 확보한다. 부족한 유형은 config 를 추가해 보충한다
- 유형별 성능 비교 시 **Macro 평균**을 사용하고, **인스턴스 수를 항상 함께 표기**한다

인스턴스 수 없이 Recall 만 제시하면 표본이 적은 유형을 "가장 어려운 유형"으로 오독하게 된다.

### 라벨은 어디까지 자동으로 나오는가

DarkAudit 의 데이터셋은 실제 금융사 화면을 수집한 것이 아니라 **직접 생성한 화면**이다. 이 점이 라벨의 성격을 바꾼다.

| 항목 | 출처 |
| --- | --- |
| bbox 좌표 | **자동** — 렌더링 시 DOM 에서 추출 |
| element_type | **자동** — DOM 태그·역할에서 추출 |
| 심은 rule_id | **자동** — 생성 설정에 기술된 값 |
| severity | 생성기가 규칙 기본값·완화 신호로 생성. 독립적인 타당성 검수는 사람 판단 |
| 결합 판정 (`combination_with`) | 규칙 정책에 따른 계산 및 독립 검수 대상 |
| **의도치 않게 발생한 패턴** | **사람 판단** |

사람이 네모를 그리지 않으므로 라벨러 간 bbox 불일치가 발생하지 않는다. 결정 ④(IoU 임계값)는 정답 라벨 간 비교가 아니라 **모델 출력과 정답 간 비교에만** 적용된다.

### Gold Set 의 목적

위 표에서 자동으로 나오지 않는 항목을 검증하는 것이 Gold Set 의 역할이다. 핵심은 마지막 줄이다.

**의도치 않은 패턴 혼입 문제.** DA-04 하나만 심으려고 체크박스를 사전선택했는데, 그 체크박스를 눈에 띄게 배치하다 보니 DA-13(감각조작)까지 성립해 버릴 수 있다. 생성 설정에는 DA-04 만 적혀 있으므로 라벨에도 DA-04 만 남는다.

이 경우 모델이 DA-13 을 정확히 탐지해도 **정답에 없으므로 False Positive 로 집계된다.** 모델이 옳고 데이터가 틀린 상황이며, 이런 항목이 쌓이면 Precision 이 실제보다 낮게 측정된다.

따라서 Gold Set 에서 두 사람은 **생성 설정을 보지 않은 상태로 화면만 보고** 라벨한다. 그 결과를 자동 생성 라벨과 대조해 다음을 확인한다.

- 자동 라벨에 없는데 사람이 찾은 유형 → 의도치 않은 혼입. 라벨에 추가하거나 화면을 수정
- 자동 라벨에 있는데 사람이 못 찾은 유형 → 심었으나 화면상 드러나지 않음. 강도를 높이거나 제외
- severity·결합 판정의 두 사람 간 일치도

### 라벨러 2인 구성의 한계와 보완

라벨링 신뢰도의 표준적 접근은 라벨러 3인 이상, 다수결에 의한 정답 확정, Krippendorff's alpha 등의 일치도 지표 산출이다. 본 프로젝트는 2인 구성이므로 다음 한계가 있다.

- **다수결이 성립하지 않는다.** 판단이 갈리면 갈린 상태로 종료된다
- **독립성이 확보되지 않는다.** 두 사람이 동일한 규칙서를 함께 작성했고 지속적으로 논의하므로, 일치율이 높게 나와도 기준이 명확해서인지 서로의 관점에 수렴한 결과인지 구분하기 어렵다
- **표본이 작다.** 20장 규모에서 산출된 일치율은 신뢰구간이 넓어 정밀한 값으로 취급할 수 없다

이를 보완하기 위해 세 가지 장치를 둔다.

**① 원문 조항에 의한 판정 (결정 ⑥).** 불일치 케이스는 다수결이 아니라 가이드라인 원문의 정의·준수사항을 근거로 판정한다. 결정 근거가 사람 수가 아니라 문서에 있으므로 2인 구성의 제약을 상당 부분 우회한다.

**② Counterfactual Pair 의 구조적 검증.** Risky/Clean 쌍은 문제 요소 하나만 다르므로 해당 rule_id 의 라벨이 반드시 뒤집혀야 한다. 뒤집히지 않으면 라벨 오류이며 자동으로 검출된다. 사람 판단과 무관하게 성립하는 검증이다.

**③ 자동 라벨과의 대조.** 위에서 기술한 바와 같이 생성 설정과 사람 판단을 교차 확인한다.

### 대외 서술 시

현재는 생성기 기반 정답과 독립 검수 미완료 사실을 함께 설명한다. Gold Set 20장·2인 일치도는 계획이며 측정한 것처럼 서술하지 않는다. 추후 측정하면 표본 수·검수자 수·불일치 조정 절차와 한계를 함께 기록한다.

## 분석 출력과 severity 구현

현재 출력 계약과 처리 코드는 다음과 같다.

| 항목 | 결론 |
| --- | --- |
| Multi-label 출력 | 가능. 같은 primary element 를 참조하는 복수 Detection 을 각각 반환 |
| 관련 요소 쌍 출력 | 가능. 라벨의 `primary`에 해당하는 대표 근거와 `related_elements`를 모델 출력에 기록. 필드 이름은 분석 스키마를 따름 |
| severity 계산 | 규칙 엔진의 `severity.py`와 분석 응답 정제·결과 저장 코드 — 아래 참조 |

### severity 계산 분담

결정적 후보의 등급 계산은 [backend/app/rule_engine/severity.py](../backend/app/rule_engine/severity.py)에 구현되어 있다. `standalone_sufficient`, `combination_amplifiers`, 완화 신호를 사용해 기본 등급과 결합·완화 결과를 계산한다. 다만 현재 탐지 단계가 모든 `mitigating_checks`를 자동 판별하는 것은 아니다.

모델은 규칙 ID, 대표·관계 요소, 관찰 근거, 신뢰도를 반환한다. 응답의 기본 등급과 유형명은 [response_parser.py](../ai/pipeline/response_parser.py)가 규칙 기준에 맞춰 정제하며, 최종 저장은 [service.py](../backend/api/service.py)의 결과 변환을 따른다. 라벨의 위험도 정책과 모델 원문 등급을 그대로 동일시하지 않는다.

### Label Validator

독립 검수에서는 라벨에 기록된 severity가 Rule Base 정책으로 계산한 결과와 일치하는지도 확인한다. 이 문서는 그 검수가 자동으로 완료되었다고 간주하지 않는다. 사람이 라벨한 severity 와 시스템 계산이 어긋나면 둘 중 하나가 잘못된 것이므로 조기에 드러난다.

## 세부 합의 사항

### element_id 를 라벨에 포함한다

`primary` 와 `related_elements` 에 DOM 기반 `element_id` 를 함께 기록한다. bbox · text 만으로 매칭하는 것보다 Counterfactual Pair 검증과 Before/After 매칭이 안정적이다.

**다만 평가의 주 키로 사용하지 않는다.** `element_id` 는 우리가 생성한 화면에만 존재하며, 실제 서비스 입력인 스크린샷에는 존재하지 않는다. 실전에서는 bbox 매칭이 유일한 수단이므로, `element_id` 를 주 키로 쓰면 벤치마크에서만 동작하고 실제 입력에서 무너지는 상황이 발생한다.

| 용도 | 사용 키 |
| --- | --- |
| Localization 평가 | bbox (IoU) |
| Counterfactual Pair 검증 | `element_id` (보조) |
| Before/After 매칭 | fingerprint, `element_id` 보조 |

### DA-11 반복 출현의 범위

최초 요구 요소를 `primary`, 이후 반복 출현을 모두 `related_elements` 에 기록한다. 최소 1개이며 상한은 두지 않되, 기존 합성 평가셋의 관찰 범위는 Flow당 5화면이다. 현재 자동 탐지 5종에는 DA-11이 포함되지 않는다.

### DA-13 의 primary 정의를 좁힌다

기존 정의는 "강조된 요소"였으나 DA-03(잘못된 계층구조)과 경계가 모호했다. MVP 라벨링에서는 **점멸 · 움직임 · 진동 · 반복 색상 변화 등 감각적 효과가 직접 적용된 요소**로 한정한다.

Rule Base 의 정의 자체는 원문(색상 · 크기 · 위치 · 스타일 변화)을 유지하되, 라벨링 범위만 동적 효과로 좁힌다. 정적 강조는 DA-03 으로 판정한다.

### IoU 임계값 (결정 ④ 확정)

- 기본 **0.5** 로 시작한다
- checkbox · radio · toggle 같은 작은 요소의 전체 클릭 영역·중심점 확인은 라벨 검수의 보조 기준이다. 현재 자동 적중률은 동일한 IoU 임계값을 적용한다

작은 요소는 면적이 작아 몇 픽셀 차이에도 IoU 가 급격히 떨어지므로 동일 기준을 적용하면 부당하게 오답 처리된다.
