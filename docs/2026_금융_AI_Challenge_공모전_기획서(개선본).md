# 2026 금융 AI Challenge 기획서

팀명: 미정(원문 유지)  
구성원: 배소연, 이정현

## 1. 서비스 명칭

DarkAudit — 생성형 AI 기반 금융상품 화면 사전점검 서비스

금융소비자보호 기준을 화면의 근거와 연결하고, 수정 후 재점검까지 지원하는 금융 UX Compliance Assistant

## 2. 아이디어 기획 핵심내용(요약)

DarkAudit은 금융상품 가입 화면에서 소비자의 선택을 왜곡할 수 있는 다크패턴을 찾아, 위치·관찰 근거·관련 기준·개선안을 함께 제시하는 웹서비스다. 금융사 기획자, UX/UI 디자이너, QA 및 금융소비자보호 담당자가 디자인과 개발 과정에서 반복적으로 사용하며, 최종 검토는 담당자가 수행한다.

핵심 문제는 정책 문서의 기준을 실제 버튼, 동의 항목, 위험 안내, 가입 단계에 연결하는 검토 부담이다. DarkAudit은 금융위원회 가이드라인의 4개 범주·15개 유형을 구조화한 규칙 기반과 멀티모달 생성형 AI를 결합해 이 작업을 지원한다. 현재 자동 분석 범위는 잘못된 계층구조, 특정옵션의 사전선택, 방해되는 절차, 감정적 언어, 순차공개 가격책정의 5개 유형이다.

사용자는 가입 순서에 따른 스크린샷 1~5장을 업로드하거나 URL 등 지원 입력을 등록한다. 시스템은 확보한 화면과 구조 정보를 분석하고, 위험 요소와 관련 선택지의 위치를 화면 위에 표시한다. 담당자는 근거와 수정안을 검토한 뒤 화면을 변경하고 재분석한다. 회차 비교 API는 이전 결과와 비교해 해결·유지·신규·재발 등의 변화를 제공한다.

React 검토 화면, FastAPI 분석·저장 API, 규칙 엔진과 멀티모달 AI를 결합한 분석 파이프라인을 구현했다. 실제 스크린샷 분석 API의 동작과 제한된 합성 사례를 검증했으며, 실제 금융사 업무에서의 정확도와 검수시간 절감 효과는 후속 실증 과제다. 미탐지, 근거 부족, 미지원 유형을 구분해 탐지 0건을 전체 규정 준수로 오인하지 않도록 한다.

## 3. 문제 정의 및 제안 배경

### 3-1. 정책 기준을 실제 화면에 적용하는 실무 부담

금융상품 가입 화면은 금리·보험료·수수료·위험정보와 선택 동의를 제한된 공간에서 제시한다. 선택 동의가 미리 활성화되거나, 거절 선택지가 지나치게 작게 보이거나, 필수 비용이 후반에 나타나면 소비자가 의도와 다른 선택을 할 수 있다. 점검 대상은 문구 자체뿐 아니라 정보의 중요도, 선택지 간 관계, 화면 간 변화다.

금융위원회는 2025년 12월 공개한 「온라인 금융상품 판매 관련 다크패턴 가이드라인」에서 4개 범주·15개 세부 유형을 제시하고, 약 3개월의 준비기간을 거쳐 2026년 4월부터 시행하는 방향을 안내했다. 금융권의 자율적인 준수와 이행상황 점검을 강조한 만큼, 화면별 검토 근거를 일관되게 남길 수 있는 실무 지원이 필요하다.[1]

### 3-2. 기존 점검 과정의 어려움

첫째, 기준과 화면의 연결을 사람이 반복해야 한다. 동일한 동의 항목이라도 필수·선택 여부, 초기 선택 상태, 주변 안내에 따라 해석이 달라진다. 디자인과 개발 단계마다 화면이 바뀌면 검토도 반복된다.

둘째, 텍스트 추출만으로는 선택 구조를 설명하기 어렵다. 문구가 중립적이어도 버튼 크기·대비·배치가 특정 선택을 유도할 수 있다. 반대로 금액 상승이 보이더라도 사용자가 선택한 옵션에 따른 변화라면 숨긴 비용으로 단정할 수 없다.

셋째, 단일 화면의 결과만으로 가입 흐름 전체를 평가하기 어렵다. 초기 고지와 최종 비용을 비교하려면 같은 상품·경로의 서로 다른 상태가 필요하다. 확인하지 못한 화면이나 상호작용은 별도 검토 대상으로 남겨야 한다.

### 3-3. 대상 사용자와 우선 적용 업무

직접 사용자는 금융사와 핀테크의 기획·디자인·QA 담당자이며, 금융소비자보호·준법 담당자가 결과를 검토한다. 소비자는 개선된 선택 환경을 통해 간접적인 보호 효과를 얻는다. 초기 실증은 보험 가입 흐름을 우선 대상으로 삼고, 예·적금·대출·투자상품으로 검증 범위를 넓힌다.

출시 전 디자인·테스트 화면을 반복 점검하는 업무에 먼저 적용한다. 수동 검토를 보조하면서 담당자가 위험 후보를 찾고 근거를 정리하는 부담을 줄이는 것이 첫 번째 가치다. 시장 내 동일 도구의 부재나 금융권 전체의 피해 규모는 검증 없이 주장하지 않는다.

## 4. 서비스 컨셉 및 차별성

### 4-1. 실제 사용 흐름

① 등록: 담당자가 Audit을 만들고 상품 가입 순서대로 화면을 업로드한다. URL 캡처, Figma 임포트, APK 수집 경로도 코드에 구현되어 있다. Figma·APK는 외부 서비스 실연동 검증이 추가로 필요하다.

② 분석: 입력에서 확보한 이미지·DOM·OCR·Figma 노드·Android XML 등의 근거를 사용한다. 규칙 엔진과 멀티모달 모델을 입력 조건에 맞게 적용하고, 근거가 부족한 판정은 별도 상태로 남긴다.

③ 검토: 화면의 위험 위치와 관련 선택지를 강조하고, 규칙 ID, 관찰 사실, 위험 이유, 개선 권고를 제공한다. 담당자는 Finding 상태를 변경하며 검토 결과를 관리한다.

④ 수정·재점검: 수정 화면을 다시 분석하고 회차 비교 API로 변화를 확인한다. 탐지 결과가 사라졌더라도 수집 범위와 검사 완료 여부를 함께 검토한 뒤 해결 여부를 확정한다.

### 4-2. 차별성: 규칙과 화면 근거를 함께 관리

15개 유형을 YAML 규칙으로 관리하고 코드로 계산할 수 있는 신호와 의미 판단이 필요한 신호를 구분한다. 생성형 AI는 문맥과 선택 관계를 해석하고 개선 문구를 제안하며, 시스템은 지원 규칙과 출력·증거 계약을 검증한다. 규칙을 문서화한 범위와 자동 탐지 구현 범위를 명확히 구분한다.

결과는 ‘어느 화면의 어떤 요소에서 무엇을 관찰했고, 어떤 기준과 관련되며, 어떻게 수정할 것인가’의 구조로 제공한다. 작은 체크박스 등은 OCR과 영상 처리 후보를 활용해 위치를 검증한다. 좌표 검증 실패나 OCR 부재도 결과의 한계로 표시한다.

### 4-3. 차별성: 관찰 범위에 맞는 흐름 분석

초기 화면과 후속 화면의 비용·선택 상태를 연결해 검토한다. URL 수집 화면은 배치로 처리하고, Figma의 프로토타입 분기는 경로를 구분한다. 현재 모든 원거리 화면 조합이나 숨은 상호작용을 포괄하는 것은 아니므로 수집 누락과 판단 근거 부족을 표시한다.

### 4-4. 차별성: 미완료 상태까지 설명하는 검토 지원

규칙별로 탐지·미탐지·근거 부족·미지원을 구분한다. 감정적 언어 등 결합 맥락이 필요한 유형을 문구 하나만으로 고위험으로 확정하지 않는다. 법 위반이나 규정 준수의 최종 판단을 자동화하기보다, 담당자가 확인할 증거와 우선 검토 대상을 제공한다.

예시: 최초 캡처에서 선택적 마케팅 동의가 활성화된 경우, DA-04 후보와 해당 위치를 제시하고 기본 해제 및 명확한 동의 안내를 권고한다. 다만 캡처 이전 사용자의 선택 이력이 확인되지 않으면 사전선택을 확정할 근거가 부족하다는 점을 함께 기록한다.

## 5. 활용 데이터 및 생성형 AI 모델 적용 방안

### 5-1. 규제 기준과 평가 데이터

규제 기준은 금융위원회 가이드라인을 바탕으로 구조화한 15개 유형의 YAML Rule Base다. 규칙 ID, 정의, 판정 조건, 의미 검토 조건과 결합 조건 등을 관리하며, 현재 자동 분석은 DA-03·DA-04·DA-07·DA-12·DA-15에 한정한다.

평가에는 자체 제작한 합성 금융 UI를 사용한다. 동일한 흐름에서 위험 요소를 바꾼 Risky/Clean 쌍으로 기본값·시각적 위계·문구·비용 공개 차이를 비교한다. 기존 평가는 22개 흐름, 110화면을 사용했다. 생성기가 심은 패턴이 정답의 출발점이므로, 독립 검수자 라벨링과 실제 화면 평가가 추가로 필요하다.

사용자 입력은 개발·테스트 화면을 우선한다. 직접 업로드와 모델 요청 1회의 화면 수는 1~5장이고, URL 수집 결과는 배치로 처리한다. 이미지 단독 입력에서는 보이지 않는 DOM 상태나 이전 사용자 행동을 확보한 사실처럼 취급하지 않는다.

### 5-2. 입력에 따라 다른 하이브리드 분석

URL에서 DOM을 확보한 경우: 화면 캡처·DOM 추출 → 규칙 엔진 후보 생성 → 멀티모달 LLM 검증 및 허용된 의미 규칙 분석 → 증거 계약 검증 → 결과 저장.

이미지 중심 입력: 이미지와 사용 가능한 OCR·노드·XML 근거 → MVP 5개 유형 시각 분석 → UI 위치 후보 검증 → 증거 계약 검증 → 결과 저장. 이미지 경로 전체를 DOM 기반 결정적 검사와 동일하다고 설명하지 않는다.

멀티모달 모델은 이미지와 텍스트를 함께 해석해 실제 대안 선택지, 필수·선택의 의미, 감정적 압박, 화면 간 비용 관계를 검토한다. 지원 범위를 벗어난 규칙이나 증거 계약을 충족하지 못한 항목은 재검증·제외하고, 유효한 다른 결과는 보존한다.

모델은 OpenAI Responses API의 이미지 입력과 구조화 출력을 활용하며 설정으로 변경 가능하다. 모델 변경 시 동일 데이터·프롬프트·평가 방식으로 정확도, 지연시간, 재시도와 사용량을 비교한다. Fake provider는 시연용으로 구분하며 정확도 평가에 사용하지 않는다.

### 5-3. 근거 위치와 과잉 판단 통제

작은 컨트롤은 OCR 라벨 주변의 색상·명암·경계·형태로 위치 후보를 만든 뒤, 확대 이미지에서 모델이 후보 ID를 선택하게 한다. 최종 위치는 선택된 후보의 원본 좌표를 사용한다. 위치 검증이 실패하면 경고를 남기므로, 모든 위치가 검증에 성공했다고 해석하지 않는다.

순차공개 가격책정은 동일 상품·경로의 초기 및 최종 금액, 단위, 사전 고지와 사용자 선택 근거를 요구한다. 비용과 수익률을 구분하고, 사용자가 선택한 부가서비스 가격 상승을 숨긴 필수 수수료와 혼동하지 않도록 한다.

### 5-4. 실증 도입 전 데이터 관리 과제

현재 분석 기록은 SQLite, 업로드·캡처 이미지는 서버의 data 경로에 저장된다. 내부 시안이나 개인정보가 포함될 수 있으므로 실증은 권한을 확보한 비식별 테스트 화면으로 시작한다. 기관 도입 전에는 외부 모델 전송 허용 범위, 계정·조직별 접근 통제, 보관·파기 정책, 마스킹 및 운영 로그 체계를 마련하고 검증할 계획이다. 이 항목들을 현재 완비된 기능으로 제시하지 않는다.

## 6. 기대 효과 및 확장 가능성

### 6-1. 기대 효과와 측정 방법

소비자 관점에서는 원하지 않는 선택 동의, 주요 위험정보 누락 인지, 비용 오해와 가입 압박을 줄이는 방향의 화면 개선을 지원한다. 실제 피해 감소 효과는 서비스 도입 전후 실증으로 확인해야 한다.

금융회사 관점에서는 검토 대상 위치와 기준을 함께 제시해 기획·디자인·QA·소비자보호 담당자의 협업을 돕는다. 동일 업무를 수동으로 수행한 경우와 DarkAudit을 활용한 경우의 화면당 검토시간, 채택된 유효 후보 비율, 수정 후 재검토시간을 비교한다. 절감률은 측정 후 제시한다.

탐지 평가는 규칙별 Precision·Recall·F1과 정상 화면 오탐률을 사용한다. 개별 요소는 규칙·화면·위치의 일대일 매칭과 IoU 0.5 기준으로 평가한다. 근거 부족 비율과 수집 도달률도 함께 보고해 일부 화면만 분석한 결과가 전체 성공률로 보이지 않도록 한다.

### 6-2. 단계별 확장

1단계는 보험 가입 흐름과 스크린샷·URL 중심의 제한된 실증이다. DA-07 오탐 개선, 독립 라벨 검수, 반복 평가를 우선 수행한다. 2단계는 Figma·APK 실제 연동을 검증하고 같은 시나리오의 입력별 수집 범위와 결과 일관성을 평가한다.

3단계는 나머지 10개 유형 중 필요한 행동·시간·화면 근거를 확보할 수 있는 유형부터 확장한다. 이후 예·적금·대출·투자상품의 검수 사례를 늘리고, 변경 화면의 자동 재점검과 CI/CD 연계를 검토한다. 현재 15개 유형 전체 자동 탐지나 CI/CD 연계가 구현된 것으로 제시하지 않는다.

### 6-3. 도입 및 사업화 가설

초기 고객 후보는 금융사 디지털 채널 조직과 금융 UX를 개발하는 핀테크·전문 제작사다. 제한된 상품 흐름의 시범 적용으로 유효 후보 비율과 검수시간 개선을 확인한 뒤, 팀·프로젝트 단위 구독 또는 기관 요구에 맞춘 구축형 제공을 검토한다. 가격·매출·도입기관 수는 고객 인터뷰와 실증 전에는 확정하지 않는다.

금융 외 영역은 규칙만 교체해 즉시 적용하기보다, 해당 정책의 해석과 업종별 UI·정답 데이터를 새로 검증하는 후속 과제로 둔다.

## 7. 구현 현황·검증 결과 및 실행 계획

### 7-1. 현재 구현과 검증 범위

구현 완료: React/TypeScript Audit 생성·결과 검토, FastAPI 업로드·분석·저장·상태 변경, URL 캡처, Figma·APK 입력 경로, MVP 5종 분석, 15종 규칙 기반, 회차 비교 API, 합성 UI 생성·평가 도구.

연동 확인: 실제 스크린샷 업로드에서 모델 호출·판정 검증·DB 저장·대시보드 응답까지의 경로. URL은 실제 Chrome DOM 추출과 모의 캡처 기반 저장 경로를 검증했다. Figma·APK는 fixture와 모의 수집기 검증이며, 실제 서비스 자격증명과 대상 파일을 이용한 연동 검증은 남아 있다.[2]

### 7-2. 제한된 데이터에서 확인한 결과

기존 합성 22개 흐름 평가에서 Rule Engine 단독 Precision/Recall/F1은 0.27/1.00/0.43, 하이브리드 3회 평균은 0.46/1.00/0.63이었다. 하이브리드 평가 모델은 gpt-5.6-luna다. 동일 평가셋에서 정밀도 개선을 관찰했지만 DA-07 정밀도는 약 0.14로, 오탐 억제가 우선 과제다.[3]

이 평가는 흐름 안에서 같은 규칙을 찾았는지 집계한 것으로, Recall 1.00이 모든 위험 요소를 빠짐없이 찾았다는 의미는 아니다. 독립 검수된 실제 금융 화면 성능이나 최신 코드 전체의 성능 보증으로 일반화하지 않는다.

별도의 스크린샷 검증은 gpt-5.4-mini로 위험/정상 10개 시나리오, 12장을 각 1회 분석했다. 의도한 규칙의 Finding 7건을 반환했고, 규칙·화면·IoU 0.5 이상을 요구하는 요소 단위 평가에서는 6건 일치, 1건 위치 불일치였다. 정상 변형에서는 탐지가 없었다. 작은 합성 사례의 동작 확인이며 두 평가의 수치나 모델을 섞지 않는다.[4]

최근 기록된 회귀 검증에서는 AI 90개, 백엔드 74개 테스트가 통과했다. 이는 코드 동작 검증이며 실제 서비스의 탐지 정확도를 뜻하지 않는다.[4]

### 7-3. 후속 8주 실행 계획(제안)

1~2주: 평가셋을 템플릿·상품 기준으로 분리하고 2인 독립 라벨링 및 불일치 조정 기준을 마련한다. DA-07 오탐 사례와 근거 부족 사례를 유형별로 정리한다.

3~4주: DA-07 규칙과 근거 검증을 개선하고, 고정된 평가셋에서 규칙별·요소별 성능을 반복 측정한다. 지연시간, 재시도, 사용량, 위치 정확도를 함께 보고한다.

5~6주: 권한을 확보한 Figma·APK·URL 테스트 대상으로 실제 수집·분석을 검증한다. 같은 가입 흐름의 입력별 도달률, 누락 화면, 초기·최종 비용 근거를 비교한다.

7~8주: 참여 실무자를 확보해 수동 검수와 도구 보조 검수를 비교한다. 유효 후보 채택률, 검토시간, 수정 전후 결과 및 미완료 상태를 확인하고 도입 조건을 정리한다. 참여기관 확보 전에는 확정 실증으로 표현하지 않는다.

담당: 배소연 — 멀티모달 분석·근거 검증·AI 평가. 이정현 — 규칙·데이터 파이프라인·백엔드·배포. 라벨 검수와 데모 검증은 공동 수행한다.

완료 기준: 동일 사례의 입력→근거 표시→담당자 검토→화면 수정→재분석 과정을 재현하고, 위험 후보 감소와 함께 수집·검사 범위가 유지됐음을 확인한다. 탐지 수치, 미완료 상태, 미검증 연동 범위를 포함한 평가 보고서를 제출한다.
